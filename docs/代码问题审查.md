# BiliTools 代码问题审查报告（修订版 v2）

> 审查范围：后端 SDK（`src/`）、桌面 GUI（`frontend/pyside6/`）、命令行入口（`main.py`）、示例与测试。
> 审查方法：逐文件阅读全部源码（约 30 个后端文件 + 20 个前端文件），结合 B 站 API 语义与并发/健壮性常识推断；对存疑结论用真实接口请求做了实测验证。
> 严重度定义：
> - **高**：会造成错误结果、数据损坏或用户不可感知的错误行为；
> - **中**：影响特定场景的正确性 / 稳定性 / 性能，或需要重启才能恢复；
> - **低**：代码卫生、UX 细节、潜在边界问题 / 防御性建议。

## 修订说明（v2）

初版报告有三条结论，经作者反馈与**真实 API 实测**后更正：

1. **原 #2「合集 bvid 入口多P只下第 1P」已证伪，撤回**。实测 `x/web-interface/view` 响应中 `ugc_season.sections[].episodes[]` **确实携带完整 `pages` 数组**：合集「洛天依·纯蓝幻乐」的唯一稿件 `BV1Q43w6QETb`（9P）episode 带 `pages` len=9；合集「明日方舟」18 个 episode 全部带 `pages`（len=1）。`VideoSeason.from_dict` 解析正确，`download_season(bvid=...)` 与 `download(bvid=...)` 均能逐P下载。初版判断依据的是过时的 BAC 文档记忆（旧文档 episode 只有单个 `page` 对象），与实际接口不符。
2. **原 #3「断点续传不校验 206」降级为防御性建议**。作者实测续传文件均正常——符合预期，因为 B 站 CDN 正确支持 Range/206。该检查缺失属于「CDN 行为异常时的兜底」，不是已观察到的缺陷。
3. **原 #1「缓存污染」保留但降级并修正触发路径**。作者指出 GUI/CLI 正常流程不会调用 `download_video`，属实（GUI 仅用 `video_with_audio`/`audio` 两种模式，CLI 仅用 `download_video_with_audio`/`download_cover`）。但该问题还有 SDK 参数级触发路径（见下 #1）。

## 二、中严重度问题

### 1. 视频流与合成视频共用缓存键（触发路径已修正）

**位置**：`src/services/video.py` —— `download_video`（L315-318）与 `download_video_with_audio`（L430-433）用**同一组**扩展名 `{"mp4", "flv", "m4s"}` 调用 `_find_downloaded_file`（L260-289，按「文件名含 bvid + 后缀匹配」查找）。

**作者反馈（采纳）**：GUI/CLI 正常流程不会调用 `download_video`（纯视频流）。核实：`download_worker.py` 仅使用 `download_audio` / `download_video_with_audio` / `download_all_pages(media_type∈{audio, video_with_audio})`；`main.py` 仅用 `download_video_with_audio` / `download_cover`。故该问题**不影响 GUI/CLI 默认使用**。

**但仍存在的 SDK 级触发路径**：

- **`keep_parts=True` 部件文件**（L496-499）：`download_video_with_audio` 会把合成前的临时流重命名为 `标题(BV).video.mp4` / `标题(BV).audio.m4a` 留在保存目录。下次对同一视频调用 `download_video_with_audio` 时，缓存检查命中 `标题(BV).video.mp4`（stem 含 bvid、后缀 .mp4），直接以 `cached=True` 返回**只有视频没有声音**的部件文件。多P场景同样成立（`标题-P02-xxx.video.mp4` 的 stem 含 `-p02`，可命中第 2P 的缓存）。
- **旧版本遗留文件**：重构前工具保存过 `BV号视频(无音频).mp4` 之类的纯视频文件，同样会被新缓存逻辑命中。

**建议**：把「合成完整视频」与「视频流部件」区分开——缓存键加入媒体形态（如完整视频只认 `.mp4` 且排除 `*.video.*` 部件）；或 `_find_downloaded_file` 增加「排除 `.video.` / `.audio.` 部件后缀」的过滤。为 `keep_parts` 场景补回归测试。

### 2. 下载 read 超时硬编码 30s

`download_stream`（`src/util/downloader.py` L80）写死 `timeout=30`，且与 `src/config/constants.py` 的 `REQUEST_TIMEOUT=15` 不一致。该 timeout 同时作用于每次 read——慢速但持续传输的连接（单块 >30s）会被误判为超时并触发重试，大文件在弱网下可能反复失败。建议改为可配置参数并接入统一超时常量。

### 3. ffmpeg 探测结果永久缓存，GUI 检测按钮形同虚设

`src/util/downloader.py` L25-35 的 `ffmpeg_available()` 首次探测后 `_ffmpeg_checked=True` 永不重置；`frontend/pyside6/pages/settings_page.py` `_on_check_ffmpeg`（L196-198）直接调用它。后果：用户安装 ffmpeg 后点「检测 ffmpeg」仍显示「未检测到」，必须重启应用。建议提供 `reset_ffmpeg_cache()` 之类的失效机制，或按钮点击时强制重新探测。

### 4. wbi key 永久缓存，无刷新机制

`src/api/auth.py` L21 的 `_wbi_keys_cache` 与 L83-100 的 `_get_wbi_keys()`：key 取一次后进程内永久缓存。B 站轮换 img_key/sub_key 后，所有 wbi 签名请求（播放流、合集、空间列表等）将因签名不匹配持续失败，且没有任何自动恢复路径。建议加 TTL 或「签名失败时清缓存重取一次」。

### 5. BiliSession 构造时固化 cookie，重新登录后旧 session 失效

`src/api/session.py` L44-49 在构造时把 cookie 写入 `self.session.headers`；`src/config/cookie.py` 的 `refresh()`（L90-99）只清类级缓存，`LoginService.save_cookie`（L203）调用 refresh 后，**已构造的 BiliSession 实例仍持有旧 cookie**。GUI 因每个任务新建 `VideoService` 而恰好规避，但任何长生命周期 session（脚本、服务、REPL）在重新登录后都会静默使用旧凭证。建议请求时从 `BiliCookies` 动态读取（带缓存），而非构造时固化。

### 6. save_cookie 只保留 5 个字段，cookie 不完整

`src/services/login.py` `save_cookie`（L186-203）的正则只提取 `SESSDATA / bili_jct / DedeUserID / DedeUserID__ckMd5 / sid`，其余全部丢弃——包括部分接口需要的 `buvid3 / buvid4` 等设备指纹字段，可能导致个别接口 -403/-412。另外 docstring 声称「含登录成功 url 中的 cookie」，但代码从未解析 URL。建议完整保存原始 set-cookie（或至少保留 buvid 系列），并修正注释。

### 7. 历史导出 view_info / detailed_info 是死功能

`src/services/history.py` `save_video_history_df`（L167-172）对 `u_like / u_coin / u_fav / num_view / num_dm ...` 用 `getattr(it, key, "")` 取值，但 `src/models/history_model.py` 的 `HistoryItem`（L12-36）**根本没有这些属性**，`getattr` 恒返回空串 → 勾选这两个选项导出的列永远为空。docstring 说「需要传入已带详情的 items」，但代码里没有任何地方能为 HistoryItem 填充这些字段。建议：要么给 HistoryItem 增加可选详情字段并由 `VideoService.fetch_info` 补充，要么从 UI/文档中移除这两个选项。

### 8. GUI 收藏夹/UP主下载双重拉取列表（具体位置）

问题出在「worker 先取列表算进度总数，service 内部又取一次」：

- **收藏夹**（`frontend/pyside6/workers/download_worker.py` L87-91）：
  ```python
  bvids = FavService(service.session).get_fav_bv(fid)      # 第 1 次：取列表算 n
  adapter = ProgressAdapter(len(bvids), f"收藏夹 {fid}", self)
  return service.download_fav(fid, save_dir, mode=mode, ...)
  ```
  而 `download_fav` 内部（`src/services/video.py` L813-816）：
  ```python
  fav = FavService(self.session)
  info = fav.get_fav_info(fid)          # 再取一次收藏夹信息
  bvids = fav.get_fav_bv(fid)           # 第 2 次：取列表
  ```
  → `get_fav_bv` 共请求 2 次（外加 1 次 `get_fav_info`）。
- **UP主**（`download_worker.py` L111-115）：
  ```python
  bvids = service.list_up_videos(mid)   # 第 1 次：完整翻页
  adapter = ProgressAdapter(len(bvids), f"UP主 {mid}", self)
  return service.download_up(mid, save_dir, mode=mode, ...)
  ```
  而 `download_up` 内部（`video.py` L923-924）：
  ```python
  mid = self._resolve_mid(mid)
  bvids = self.list_up_videos(mid)      # 第 2 次：完整翻页
  ```
  → UP主空间的分页遍历（`list_up_videos` 每页一个 wbi 签名请求）完整执行两遍。

**影响**：(a) 列表获取的 API 请求翻倍（UP主场景是整页遍历翻倍，额外消耗 wbi 签名与风控额度）；(b) 两次拉取之间列表若变化（收藏夹增减、UP主新投稿），`ProgressAdapter` 的 `n`（第一次结果）与 service 实际遍历的列表（第二次结果）不一致，进度显示总数与实际下载数失配。

**建议**：worker 只负责构造参数并传入 adapter，让 service 提供「先取列表再下载」的单一入口（如 `download_fav`/`download_up` 返回总数，或接受外部传入的列表）；至少应复用第一次的列表结果。

### 9. normalize_bvid 在 UI 线程同步请求网络

`frontend/pyside6/utils.py` `normalize_bvid`（L69-81）：输入短链接/非标准链接时在**点击下载的 UI 线程**同步 `requests.get(..., timeout=15)` 解析重定向，期间界面完全冻结，最坏 15 秒。建议把链接解析放进 worker 线程，或仅支持本地可解析的输入（BV/av/完整链接），对短链接提示用户先打开。

## 五、测试覆盖缺口

现有测试（`tests/`，57+ 单元 / 18 网络）质量不错，已覆盖文件名、cookie、wbi、模型、进度等，且 `test_services_bilibili.py` 有真实网络的多P/合集用例。建议补充：

1. **缓存污染回归**：先 `keep_parts=True` 下载留下 `标题(BV).video.mp4` 部件，再 `download_video_with_audio` 应**重新下载**而非命中部件缓存（当前会错误命中）；
2. **断点续传异常 CDN**：模拟服务器忽略 Range 返回 200 时，不应追加写坏文件（配合 #10 修复）；
3. **wbi key / ffmpeg 缓存失效**：设计「失败后强制刷新」的可注入点并测试。

## 七、结论

BiliTools 的**分层与工程结构是健康的**：统一请求层、异常体系、路径锚点、命名规范执行得相当一致；实测确认合集 bvid/sid 双通道的分P解析均正确，断点续传在 B 站 CDN 下工作正常。

修订后的问题集中在四类：

1. **缓存语义**——「媒体形态」未进入缓存键（#1），但触发路径限于 SDK 的 `keep_parts=True` 部件文件与旧版遗留文件，不影响 GUI/CLI 默认流程；
2. **进程级缓存的失效机制**——ffmpeg 探测、wbi key、session cookie 三处都缺刷新路径（#3/#4/#5）；
3. **重复请求**——GUI 收藏夹/UP主下载列表被拉取两遍（#8）；
4. **死功能与文档失真**——历史导出选项、save_cookie 注释等（#6/#7）。

建议按 P1/P2 批次推进，并优先补 #1 的回归测试。
